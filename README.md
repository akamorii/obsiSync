# obsiSync

Синхронизация папки (например, хранилища Obsidian) между устройствами через git-репозиторий.
Папка упаковывается в zip, шифруется ключом из `.env`, режется на сегменты и пушится в репо
папкой с текущей датой. При получении скачивается только последний архив.
На другом устройстве архив скачивается, расшифровывается и аккуратно вливается в локальную папку,
не затирая локальные изменения.

## Установка

```bash
python3 -m venv venv
venv/bin/pip install -r requirements.txt
```

Нужен установленный `git` с доступом к репозиторию (SSH-ключ или токен) и настроенными `user.name` / `user.email`.

## Настройка

```bash
venv/bin/python setSettings.py
```

Скрипт спросит только то, чего ещё нет:

- ключ шифрования — сохраняется в `.env` как `SECRET_KEY`;
- ссылку на git-репозиторий — `repo.link` в `config.yml`;
- абсолютный путь к синхронизируемой папке — `storage.absolutePath` в `config.yml`.

Пример `config.yml`:

```yaml
crypt:
  encrypted: true        # false — пушить обычный .zip без шифрования
repo:
  link: git@github.com:user/vault-backup.git
  segmentSize: 45        # размер сегмента в МБ (GitHub не принимает файлы > 100 МБ)
storage:
  absolutePath: /Users/user/Documents/Vault
```

На всех устройствах `SECRET_KEY` должен быть одинаковым, иначе архив не расшифруется.

## Использование

Отправить папку в репо:

```bash
venv/bin/python main.py -s
```

Получить изменения из репо:

```bash
venv/bin/python main.py -f
```

### `-s` (send)

1. Подтягивает последний коммит репо в `./repo` (см. «Что скачивается»).
2. Если в репо уже есть архив, сначала вливает его в локальную папку (как `-f`),
   чтобы не потерять изменения, сделанные на другом устройстве.
3. Упаковывает папку в zip (папки `.git` пропускаются) и шифрует его.
4. Режет архив на сегменты по `segmentSize` МБ и кладёт их в папку `YYYY-MM-DD/`.
   Если папка за сегодня уже есть, она заменяется целиком.
5. Делает commit и push.

### `-f` (fetch)

1. Подтягивает последний коммит репо.
2. Находит самую свежую папку с датой и скачивает только её сегменты.
3. Собирает архив из сегментов, проверяет sha256, расшифровывает и распаковывает во временную папку.
4. Вливает файлы в локальную папку через модуль `synchronize`.

## Сегменты

Архив в репо выглядит так:

```
2026-10-09/
  manifest.json          # имя архива, размер, sha256, список частей
  vault.zip.enc.000
  vault.zip.enc.001
  ...
```

При сборке проверяется, что все части на месте и sha256 совпадает с `manifest.json`.
Если чего-то не хватает или данные повреждены, выводится ошибка, локальная папка не меняется.

## Что скачивается

`./repo` — это не полный клон, а:

- `--depth 1` — только последний коммит, без истории;
- `--filter=blob:none` — без содержимого файлов, только структура папок;
- `sparse-checkout` — содержимое скачивается только для папки, с которой идёт работа
  (последний архив при `-f`, папка за сегодня при `-s`).

Поэтому старые архивы в репо не скачиваются, сколько бы их ни было.
Если `./repo` был создан старой версией скрипта (полный клон), он пересоздаётся автоматически.

## Как работает слияние

`synchronize.py` сравнивает три версии каждого файла:

- **local** — файл в локальной папке;
- **remote** — файл из архива;
- **base** — хэш файла на момент последней синхронизации (`.sync_state.json`).

| Ситуация | Результат |
|---|---|
| Изменён только в архиве | Обновляется локально |
| Изменён только локально | Остаётся локальная версия |
| Новый файл в архиве | Добавляется |
| Удалён в архиве, локально не менялся | Удаляется локально |
| Удалён локально, в архиве не менялся | Остаётся удалённым |
| Изменён с обеих сторон | Локальный остаётся, версия из архива сохраняется рядом как `name.conflict-<дата>.ext` |

Конфликтные копии нужно разобрать вручную. После следующего `-s` они попадут в репо как обычные файлы.
Если `.sync_state.json` нет (первый запуск), ничего не удаляется, а различающиеся файлы считаются конфликтом.

## Шифрование

Ключ из `.env` хэшируется через PBKDF2-SHA256 (600 000 итераций) со случайной солью.
Соль записывается в начало файла, остальное — токен Fernet (AES-128-CBC + HMAC-SHA256).
При неверном ключе или повреждённом файле выводится ошибка, локальная папка не меняется.

## Структура

| Файл | Назначение |
|---|---|
| `main.py` | Точка входа, флаги `-s` / `-f` |
| `setSettings.py` | Интерактивная настройка, `loadConfig()` |
| `gitScript.py` | shallow + sparse клон, commit / push, поиск последнего архива |
| `crypto.py` | Шифрование и расшифровка файлов |
| `segment.py` | Нарезка архива на сегменты и сборка с проверкой sha256 |
| `synchronize.py` | Трёхстороннее слияние папок |
| `config.yml` | Настройки |
| `.env` | `SECRET_KEY` (не коммитится) |
| `repo/` | Локальная копия репозитория (не коммитится) |
| `.sync_state.json` | Хэши файлов на момент последней синхронизации (не коммитится) |

## Ограничения

- Повторная отправка в тот же день перезаписывает папку дня. Старые версии остаются в истории git.
- Сегментация обходит лимит GitHub на размер одного файла (100 МБ), но не на размер репозитория
  (рекомендуется до 1–5 ГБ). Каждая отправка добавляет в историю новый архив, поэтому репо со временем растёт.
- Если между `-s` на двух устройствах кто-то успел запушить, push отклоняется — достаточно запустить команду ещё раз.
- Архив целиком загружается в память при шифровании, для очень больших папок это может быть заметно.
